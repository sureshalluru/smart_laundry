# Garment Counter — Backend API Contract

This document is the contract the **Garment Counter iPad app** expects from the
backend(s). It is the source of truth for the Jetson + EC2 developers.

A complete, runnable reference implementation of every endpoint below lives in
[`mock-server/server.mjs`](./mock-server/server.mjs). To see any endpoint's
exact behavior, run it and hit it with curl/Postman:

```bash
cd apps/garment-counter
npm run mock          # listens on http://localhost:4000
curl http://localhost:4000/single_cloth/
```

The app is server-agnostic: both base URLs are entered by the operator in the
app's **Settings** screen. There is nothing hardcoded.

---

## Two servers, two responsibilities

| Server | Reached over | Responsibilities |
|--------|--------------|------------------|
| **Jetson** (camera device) | Local network (LAN) | Start / stop a counting transaction |
| **EC2** (cloud backend) | Internet | Detections, corrections, counts, history, dashboard |

The Jetson pushes detections to EC2; the iPad **polls EC2** for them. The iPad
never talks to the Jetson for detection data — only to start/stop.

---

## Core object: `DetectionEvent` (snake_case on the wire)

Every detection the EC2 endpoints return uses this shape:

```json
{
  "cloth_id": 42,
  "cloth_type": "shirts",
  "file_path": "captures/2026-02-01/42.jpg",
  "date": "2026-02-01T10:15:30.000Z",
  "ismodified": false,
  "wash_type": "Before Wash",
  "trans_id": "IS-1042",
  "operator_name": "Jane Doe",
  "uniq_id": "9f1c...uuid",
  "status": "ok",
  "confidence": 87
}
```

| Field | Type | Notes |
|-------|------|-------|
| `cloth_id` | integer | **Monotonically increasing.** See "cloth_id contract" below. Required. |
| `cloth_type` | string | Category label, e.g. `shirts`, `pants`, `towels`. Required. |
| `file_path` | string | Path/URL to the captured image (see "Images"). Required. |
| `date` | string | ISO 8601 timestamp. Required. |
| `ismodified` | bool | `true` after a manual correction. |
| `wash_type` | string | `"Before Wash"` or `"After Wash"`. Required. |
| `trans_id` | string | The order id. Required. |
| `operator_name` | string | Logged-in employee. Required. |
| `uniq_id` | string | Session UUID generated by the iPad. Required. |
| `status` | string | Free-form status. Required. |
| `confidence` | number (0–100) | Optional. Below 70 is flagged low-confidence in the UI. |

> The iPad **normalizes** this payload internally. Missing a *required* field
> means the app treats the record as malformed and skips it, so please always
> include the required fields.

---

## The `cloth_id` contract (important)

The app detects "new" items purely by `cloth_id`:

- A detection is **new** if and only if its `cloth_id` is **strictly greater**
  than the highest the app has seen this session.
- `cloth_id` must therefore be **monotonically increasing** within a session.
- Gaps are fine (offline catch-up relies on this); duplicates and lower values
  are ignored as already-seen.

If two different garments ever reuse a `cloth_id`, the second is silently
dropped. Please guarantee uniqueness + increase per detection.

# Jetson endpoints (LAN)

### `GET /transaction/` — start a transaction

Called when the operator starts a counting session.

Query params (all URL-encoded):

| Param | Example | Meaning |
|-------|---------|---------|
| `id` | `IS-1042` | Order id (`trans_id`) |
| `type` | `Before Wash` | `Before Wash` or `After Wash` |
| `operator_name` | `Jane Doe` | Employee name |
| `uniq_id` | `9f1c-...` | Session UUID (generated by the iPad) |
| `date` | `2026-02-01T10:15:30.000Z` | ISO start time |

Example:
```
GET /transaction/?id=IS-1042&type=Before%20Wash&operator_name=Jane%20Doe&uniq_id=9f1c...&date=2026-02-01T10:15:30.000Z
```

Responses:
- `200` → `{ "success": true }` — transaction started, camera begins detecting.
- `409` → another transaction is already running on the camera. The app shows
  "another transaction is already running" and does **not** start.

### `POST /transaction/` — stop the active transaction

Form-encoded body (`application/x-www-form-urlencoded`):

```
status=0&uniq_id=9f1c...
```

- `200` → `{ "success": true }`

# EC2 endpoints (cloud)

### `GET /single_cloth/` — latest detection  ⏱ polled every 500 ms

Returns the **single most recent** detection for the active session, or `{}`
when there is none yet.

- `200` → a `DetectionEvent`, or `{}`
- The app polls this at **500 ms**. Keep it fast and cheap.
- A failed/timed-out response flips the "Cloud" indicator to offline; success
  flips it back. So a healthy 200 is also the connectivity signal.

### `POST /single_cloth/` — correct the latest cloth's category

Body (`application/json`):
```json
{ "cloth_id": 42, "category": "pants" }
```
- `200` → `{ "success": true }`. On success the app moves the item to the new
  category. On non-2xx it keeps the item where it was and shows a retry toast.

### `POST /move_cloth/` — resolve a discrepancy

Body (`application/json`):
```json
{ "cloth_id": 42, "target_category": "towels", "trans_id": "IS-1042" }
```
- `200` → `{ "mismatch_resolved": true, "new_status": "balanced" }`
- The app marks that category resolved when `mismatch_resolved` is `true`, and
  displays `new_status` if provided.

### `GET /cloth_count/single_transaction/?uniq_id=X` — items for a session

- `200` → array of `DetectionEvent` for that session UUID.
- Used to render the History detail and per-session tallies.

### `GET /cloth_count/before_wash/?trans_id=X` — Before Wash items for an order

The iPad knows the **order id** but not the prior Before Wash session's
`uniq_id`, so this must resolve it server-side.

- `200` → array of `DetectionEvent` from the order's Before Wash session (empty
  array if none).
- Used to build the After Wash comparison baseline and the discrepancy photo view.

### `GET /transaction/check/{trans_id}/` — does a Before Wash exist?

- `200` → `{ "exists": true }` (also accepts `{ "before_wash_exists": true }`)
- Called before starting **After Wash**; if `false`, the app blocks the start
  and tells the operator to do Before Wash first.

### `GET /transaction/history/?operator_name=X` — session history

- `200` → array of:
  ```json
  { "trans_id": "IS-1042", "uniq_id": "9f1c...", "type": "Before Wash",
    "operator_name": "Jane Doe", "date": "2026-02-01T10:15:30.000Z" }
  ```

### `GET /orders/summary/` — dashboard rollup (per order)

- `200` → array of:
  ```json
  {
    "trans_id": "IS-1042",
    "operator_name": "Jane Doe",
    "date": "2026-02-01T10:15:30.000Z",
    "before_total": 8,
    "after_total": 7,
    "before_by_category": { "shirts": 5, "pants": 3 },
    "after_by_category":  { "shirts": 4, "pants": 3 },
    "has_before": true,
    "has_after": true,
    "mismatch": true
  }
  ```
- Powers the Orders Dashboard (Before/After totals + mismatch flag per order).

## Images

Each `DetectionEvent.file_path` is resolved by the app as:

```
<EC2 base URL>/<file_path>
```

So `file_path: "captures/42.jpg"` with EC2 base `https://api.example.com`
becomes `https://api.example.com/captures/42.jpg`.

- The EC2 backend must serve these images at that path.
- **Retention matters:** the After Wash comparison shows the *Before Wash*
  photos, which may be hours old. Intake images must remain reachable until the
  order's After Wash reconciliation is complete — do not purge them at
  transaction close.

## Cross-cutting requirements

1. **CORS.** Both servers must return
   `Access-Control-Allow-Origin` for the iPad app's origin (and handle
   `OPTIONS` preflight for the JSON `POST`s). The mock uses `*` for convenience;
   production should scope it to the app's real origin.

2. **HTTPS / mixed content (biggest gotcha).** If the app is served over HTTPS
   (e.g. `https://.../counter/`), browsers **block** calls to `http://`
   endpoints. Either:
   - serve the app over HTTP from the LAN, **or**
   - give the Jetson and EC2 valid HTTPS certs.
   Please decide this early — it affects how the Jetson exposes its LAN endpoint.

3. **Trailing slashes.** The app calls paths exactly as written above
   (`/transaction/`, `/single_cloth/`, etc., with trailing slash). Match them.

4. **Polling load.** `GET /single_cloth/` is hit every 500 ms per active iPad.
   Make it cheap (single-row lookup, no heavy joins).

## How to try the reference now

```bash
cd apps/garment-counter
npm install
npm run mock     # terminal 1 — the reference backend on :4000
npm run dev      # terminal 2 — the app on http://localhost:5180/counter/
```

In the app: **Settings** → set both Camera and Cloud URLs to
`http://localhost:4000` → start a Before Wash session and watch it work.
Inspect the exact traffic in the browser Network tab, or curl the mock directly.
